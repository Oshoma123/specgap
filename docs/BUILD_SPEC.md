# Build spec — SPECGAP

PROJECT
SPECGAP: an open engine for assessing the coverage of public MS/MS spectral
libraries against public natural-product structure databases, and the audits
it produces. Archetypes stacked: Pipeline/tool (2) + Open dataset (1) +
Analysis paper (8).

QUESTION
Of the natural-product structures documented in LOTUS and COCONUT, what
fraction have at least one matching MS/MS spectrum in GNPS, MassBank, or
MoNA (structural coverage)? Separately, of the entries in those spectral
libraries, what fraction carry a compound name that can be correctly
recovered against the structure databases (name-recoverability)? Both
measures broken out per source and per source-pair.

SOURCES (confirmed live 2026-09-01)
| Source | URL | Vintage | License | Bulk access |
|---|---|---|---|---|
| LOTUS | lotus.naturalproducts.net/download | rolling, frozen releases on Zenodo | data CC0 (Wikidata-backed) | SDF, MongoDB dump |
| COCONUT 2.0 | coconut.naturalproducts.net/download | Aug 2026 | CC0 | CSV, SDF, Postgres dump, REST API |
| GNPS | external.gnps2.org/gnpslibrary | last full export 2026-03-29, 2,904,572 spectra | CC0 (default reference spectra) | mgf, msp, json; Zenodo archives |
| MassBank | github.com/MassBank/MassBank-data, massbank.eu | NAR 2026-01-06 release, 119,845 spectra / 18,529 compounds | CC BY 4.0 | per-record flat files, versioned releases with DOI |
| MoNA | mona.fiehnlab.ucdavis.edu/downloads | ~3,596,790 records | mixed, per-record (many CC0/CC-BY, some restricted) | SDF/JSON/MSP bulk export |

UNIT OF ANALYSIS
One unique chemical structure, keyed on InChIKey. Structural coverage is also
reported at the InChIKey-skeleton level (first 14 characters, ignoring
stereochemistry/isotope layers) since spectral libraries frequently cannot
resolve full stereochemistry.

MEASURES
- `structural_coverage`: share of the LOTUS ∪ COCONUT structure set with
  ≥1 matching spectrum in GNPS ∪ MassBank ∪ MoNA, by full InChIKey and by
  skeleton, reported overall and per spectral source.
- `name_recoverability`: share of spectral-library entries whose declared
  compound name (exact match after normalization, then fuzzy match at a
  fixed threshold) resolves to a name/synonym recorded in LOTUS/COCONUT for
  the same InChIKey. Reported per spectral source.
- Both stratified by ionization mode where recorded.

OUTPUTS
- `data/processed/coverage_audit.csv` — one row per structure-database entry
- `data/processed/name_recoverability.csv` — one row per spectral-library entry
- `data/processed/qa_report.txt`, `data/processed/stats.json`
- `paper/figures/coverage_by_source.png`
- `paper/paper.md` (JOSS-style software paper) + `docs/AUDIT_REPORT.md` (data descriptor)
- GitHub repository, Zenodo-deposited dataset release with DOI

VENUES
1. GitHub + Zenodo (DOI) — repo and first coverage-audit dataset release.
2. JOSS — the matching engine itself, once it has run on the full data and has tests.
3. ChemRxiv or a data-journal descriptor — the audit findings.

VERIFY POINTS (author must personally rule on these)
- InChIKey-skeleton matching as the primary coverage criterion vs. requiring
  full-InChIKey (stereochemistry-exact) matches — this build defaults to
  reporting both, author picks the headline number.
- Name-normalization and fuzzy-match threshold (default: casefold, strip
  salts/hydrate suffixes, Levenshtein ratio ≥ 0.92) — affects
  name-recoverability materially.
- Whether MoNA records without an explicit open license are included in
  "public spectral library" counts or excluded (default: excluded from the
  headline number, included in a supplementary count).

ASSUMPTIONS AND SANDBOX CONSTRAINT — READ BEFORE TRUSTING ANY NUMBER
This build environment has no outbound network access for code execution.
`01_fetch.py` is written against the real endpoints above and will pull the
real bulk files when run on a machine with network access. To prove the
pipeline is correct end-to-end, this build ships and runs against a small
**synthetic fixture** (`data/raw/fixtures/`, ~40 records per source,
generated by `code/00_make_fixture.py`, clearly labeled SYNTHETIC
throughout). Every number currently in `stats.json`, every figure, and the
draft manuscript text describe the **fixture run only** and are not real
coverage findings. The author must re-run `01_fetch.py` against live data
before any of this is cited, published, or used to draw a scientific
conclusion. `publish_gate.py` will not catch this distinction — it is
flagged here and in every generated document's status line instead.
